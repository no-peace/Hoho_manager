# Task 1: Implementation Plan (Phases and Tasks)  

## Phase 1: Enhance Security and Permissions  
- **Audit all permission logic:** Ensure **staff permission checks** uniformly apply at every entry point. For example, every “send message” or “view message” route should enforce both `assertStaffChannelAllowed()` and `assertStaffGuildAllowed()`. Likewise, review `/api/receive` or interaction routes to prevent unauthorized access. Add regression tests for each case (e.g. “staff in wrong guild gets 403”).  
- **Review admin vs staff contexts:** Confirm that any route marked `requireStaffPermission` or similar properly distinguishes admin vs staff. Verify that admins (using `x-admin-key`) are not accidentally blocked by allowlists. Add tests for admin access to restricted channels/guilds.  
- **Sanitize and validate inputs:** Wherever user-provided data is saved (backup names, webhook URLs, message content), apply strict validation. For instance, ensure backup names aren’t injection vectors, and webhook URLs match Discord’s expected format. This follows best practices of *validating external input before processing*.  

## Phase 2: Expand Test Coverage and Monitoring  
- **Regression tests for permissions:** In `server/tests/routes.test.ts`, add cases for: “GET `/api/access` as staff (should be forbidden) vs admin (should work)”, and for `/channels/:cid/messages/:mid` as a forbidden guild (should 403). Similarly test the new tracking endpoints (`POST /api/track` and `/sync`). Use mocks for Discord APIs (already done for channel-guild).  
- **Core workflow tests:** Write Vitest or supertest suites for new features. E.g. simulate creating a backup, scheduling it, and deleting old unscheduled backups. Test the `/api/discord/identity` route returns correct bot info. Verify that `{user<id>.…}` placeholders are resolved correctly in both preview and send pipelines. Use automated tests for error cases and edge conditions (empty payloads, invalid IDs, etc.).  
- **CI/CD integration:** Ensure tests run on every push (e.g. GitHub Actions). Use coverage tools to identify untested lines. According to best practices, *“write automated tests for core business logic and run them in CI”*. Fail the build on test failures.  

## Phase 3: Database Optimization and Cleanup  
- **Schema review:** Inspect the migrations and database schema. Remove unused tables/columns (e.g. drop `webhook_profiles` if still present, drop any deprecated audit logs). Consolidate data types if necessary (ensure snowflake IDs use INTEGER with appropriate size).  
- **Normalization and indexes:** Apply normalization rules so related data is not duplicated. For high-frequency queries (e.g. looking up tracked messages, or filtering by user or channel), add indexes. For example, index `staff.allowed_channel_ids` or `tracked_messages.message_id` if queried often. Follow SQLite tuning advice: *“Design your database schema… Properly index tables to enhance performance”*, and only **select needed columns** in queries.  
- **PRAGMA and concurrency:** In local SQLite, ensure WAL mode and `PRAGMA synchronous=NORMAL` are set (as recommended for speed at minimal durability cost). If using Turso, investigate support for transactions and atomicity, since the current adapter skips real transactions. Consider adding integrity checks or foreign keys if not present.  
- **Data retention:** Implement the requested backup retention logic. For unscheduled backups, schedule a cleanup job (in `maintenanceService.ts` or a new cron job) to delete items older than 14 days. For scheduled backups, add a “keepUntil” date field (in the backups table) that users can set; allow cleaning data only past that date. These rules mirror Discohook’s design: e.g. *“schedule times must be at least 30s in the future; cron no more than every 2h”*, and un-used items are eventually pruned.  
- **Minimize wasted storage:** Check that only necessary fields are stored. For example, once a tracked message is sent and no longer needed, remove any heavy payload fields (or archive them) if appropriate. The Android SQLite docs emphasize *“read only the rows/columns you need”*; similarly, avoid storing large JSON/objects unless required.
